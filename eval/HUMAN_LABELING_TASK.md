## 为什么需要人来做

这个项目用一个确定性规则引擎做初筛，产出的是「候选」。但规则的对错只能靠人判断：
一条报告到底算不算缺陷，只有读过它的人知道。**写这份任务书时**，全部数字还都是
「规则和写规则的人之间的一致度」，这在方法上等于自己给自己打分。

**当时**所以需要第二个独立读者，在不看规则输出的情况下判一遍。这个缺口后来由
G 集四位独立真人补上；v2 规则下的读者-读者 κ 则按决定不再测。详见顶部状态提示。
下面第 3 步之后仍然是当时通用的判定规则，可继续用于复核已有标注。

**这不是考试。** 没有标准答案，也没有及格线。你判得和规则不一样，恰恰是最有价值的部分。

## 判定规则

只问一件事：**这条报告有没有在主张「某个功能坏了 / 行为和预期不符 / 环境里出了错」。**

**算缺陷**

- 报错、崩溃、抛异常、贴 traceback
- 数据不对：丢失、截断、重复、顺序错、导出内容不对
- 界面坏：错位、被遮挡、点了没反应、焦点跳走、不刷新
- 配置或环境变量写了不生效；安装失败
- 「以前能用，某版本之后不能用了」
- 逻辑判错、非法输入被接受、同一个操作被执行两次

**不算缺陷**

- 功能请求：「希望支持……」「能不能加个……」「建议增加……」
- 提问：「怎么才能……」「为什么我这里是……」（没有主张坏了）
- 纯讨论、经验分享、方案对比
- 赞助、推广、招聘、活动通知
- 只有标题没有内容，或只贴了一个版本号

**边界（按这个判）**

- 主线在报问题、末尾顺带提了个功能请求 → **算缺陷**，类别按主问题填
- 在问「怎么配置」但实际是在说「配了没用」 → **算缺陷**（配置不生效）
- 报告里贴了大段代码或日志 → 判断这段代码在说明什么问题，代码本身不是类别
- 读两遍还是拿不准 → 填 **不确定**，F 列写清卡在哪一步

## 类别速查

E 列**只能**从下表第一列选，不要自己造词。

| 类名 | 什么时候算 |
|---|---|
| `crash_or_error` | 崩溃、未捕获异常、traceback、段错误 |
| `data_integrity` | 数据丢失、截断、损坏、重复、计数错、导出/导入内容不对 |
| `config_or_env` | 环境变量或配置写了不生效、被忽略；依赖装不上 |
| `ui_or_ux` | 布局错位、被遮挡、点击无响应、焦点丢失、渲染不刷新 |
| `i18n_or_locale` | 翻译缺失或错、回落到英文、区域/日期格式不对 |
| `security` | 路径穿越、越权、绕过确认、任意命令执行、凭证泄露 |
| `performance` | 卡死、超时、内存泄漏、明显变慢（不是「有点慢」） |
| `regression` | 以前能用现在不能用、某个版本之后坏掉 |
| `docs` | 文档缺步骤、README 写错、照着文档装不起来 |
| `logic_or_validation` | 逻辑判断错、类型转换错、非法输入被接受、重复执行、校验缺失 |

一条报告可以同时属于多类。比如一个导出功能把数据截断了：`crash_or_error, data_integrity`。
